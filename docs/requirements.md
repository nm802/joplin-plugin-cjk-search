# 要件定義: joplin-plugin-cjk-search

Joplin の検索が日本語・日英混在テキストで取りこぼす問題を、独自 n-gram 索引を持つプラグインで解決する。

## 1. 背景 — 現行 Joplin の実測結果

joplin CLI（本物の `@joplin/lib` SearchEngine、索引12/12構築済み）に検証用ノートを投入し、Data API 経由で検索した実測値。推測ではなく計測結果。

### 1-1. 検索経路が2つに分岐している

`SearchEngine.determineSearchType_()` は**クエリの文字種だけ**を見て経路を決める。

- クエリに CJK 文字が含まれる → `SEARCH_TYPE_NONLATIN_SCRIPT` → 生の `notes` テーブルに `LIKE '%...%'`
- それ以外 → `SEARCH_TYPE_FTS` → `notes_fts`（FTS4 / `simple` トークナイザ）

ノート側が日本語かどうかは判定に入っていない。

### 1-2. FTS 経路: 日本語本文に埋まった英数語が引けない

FTS4 の `simple` トークナイザは「ASCII 英数字以外かつ 0x80 未満の文字」を区切りとする。日本語文字（すべて 0x80 以上）は区切りにならず、トークンに飲み込まれる。

本文 `型番メモ 型番QZ-4700の熱設計を検討する` から生成された実トークン:

```
'型番メモ'
'型番qz'
'4700の熱設計を検討する'
```

本物の `notes_fts` への直接 MATCH 結果:

```
MATCH 'qz-4700*'  -> 0件
MATCH 'qz*'       -> 0件    前方一致はトークン先頭からしか効かない
MATCH '4700*'     -> 1件    ハイフン直後がトークン先頭になった偶然
MATCH '熱設計*'    -> 0件    日本語はトークン途中なので届かない
```

区切り記号の直後に来た部分だけが偶然引ける。同じ型番でも本文の書き方で結果が変わる:

```
本文「型番QZ-4700の熱設計」    → 「QZ-4700」× 「QZ」× 「4700」○
本文「型番 QZ-4700 の熱設計」  → 「QZ-4700」○ 「QZ」○ 「4700」○
```

### 1-3. LIKE 経路: クエリだけ正規化され、本文は生のまま

`SearchEngine.parseQuery()` はクエリに `normalizeText_()`（NFC・小文字化・`\s`→半角スペース・Latin diacritics 除去）をかける。ところが `queryBuilder.ts:351` の LIKE 対象は生の `notes.body` で、正規化済みの `notes_normalized` ではない。FTS 経路は `notes_normalized` を見ているため、この非対称は日本語経路だけで起きる。

実 DB で同じパターンを両テーブルに当てた結果:

```
notes            (生)       LIKE '%api%'  ->  m2, n2
notes_normalized (正規化済)  LIKE '%api%'  ->  m2, n1, n2
```

```
n1  notes(生)        = 'この機能のＡＰＩは別紙参照'    ← 全角のまま
n1  notes_normalized = 'この機能のapiは別紙参照'
```

結果、全角英数で書かれた本文は全角で検索しても半角で検索しても引けない。

### 1-4. LIKE 経路: markdown 記号と改行が複合語を分断する

LIKE は生の markdown 本文への部分一致なので、語の途中に記号や改行が入るとまたげない。

```
n5 =「屋根の防水工事が必要になる」
n6 =「屋根の**防水**工事を実施した」
n7 =「屋根の防水\n工事を実施した」

検索「防水」      -> n6, n7, n5
検索「防水工事」   -> n5 のみ      n6, n7 が落ちる
検索「屋根の防水」 -> n7, n5       n6 が落ちる
```

このうち**記号（n6）だけを直す対象とする。改行（n7）は直さない**（FR-3）。改行は語の区切りとして扱うため、このプラグインでも n7 は `防水工事` で引けない。

### 1-5. 実測サマリ（全12ノート・索引完了状態）

```
検索「API」        -> 0件        日本語文中の API が引けない
検索「ＡＰＩ」      -> m2, n2     全角で打つと LIKE 経路に落ちて引ける（半角本文のみ）
検索「機能のＡＰＩ」 -> n2         全角本文の n1 は出ない
検索「QZ-4700」    -> 0件
検索「4700」       -> m1
検索「雨漏り 対応」 -> n5, n4, n3  半角スペース区切りは AND として機能する
検索「雨漏り　対応」-> n4          全角スペースだと1件に激減
検索「がんぼう」    -> 0件         本文が NFD 濁点
```

### 1-6. 表示側の上限

`GotoAnything.tsx:397-415` は body 一致がある場合に結果を 20 件へ切り詰める。非 FTS 経路では `processNonFtsSearchResults_()` が全行に `body` フラグを立てるため、日本語検索では常にこの分岐に入る。また非 FTS 経路は `weight` が 0 のままで、順序は「タイトル一致優先 → 更新日時降順」だけになる。

## 2. 目的

**言語に依存しない単一の検索経路を提供する。** 日本語・英語・日英混在を区別せず、同じ索引・同じ正規化で引けるようにする。

現行の「クエリの文字種で経路が変わり、どちらの経路にも別々の取りこぼしがある」構造そのものを置き換える。

## 3. スコープ

### やる

- Joplin プラグインとして独自 n-gram 索引を構築・維持する
- 索引は `joplin.plugins.dataDir()` 配下の独自 SQLite ファイルに置く
- 独自の検索 UI を提供し、Ctrl+P に割り当て可能にする
- ノート変更・同期完了に追従して差分更新する

### やらない

- Joplin 本体のコード変更（別途 upstream PR として検討するが、このリポジトリの対象外）
- Joplin 本体の DB (`database.sqlite`) への書き込み
- セマンティック検索・埋め込みベクトル
- モバイル版対応（`joplin.require` はデスクトップ限定）

## 4. 機能要件

### FR-1 正規化の対称性

索引時とクエリ時に**同一の正規化関数**を適用する。片側だけに適用してはならない。

正規化方式は **NFKC + casefold + かなの畳み込み**。実測で、観測された全ての取りこぼしケースを両側で一致させられることを確認済み:

```
全角英数    'ＡＰＩ'      -> 'api'      / 'API'      -> 'api'      一致
半角カナ    'ｻｰﾊﾞｰ'      -> 'サーバー'  / 'サーバー'  -> 'サーバー'  一致
全角スペース '雨漏り　対応' -> '雨漏り 対応'/'雨漏り 対応'-> '雨漏り 対応' 一致
NFD濁点     'がんぼう'(NFD)-> 'がんぼう' / 'がんぼう'(NFC)-> 'がんぼう'  一致
全角数字    'Ｖｅｒ２'     -> 'ver2'     / 'Ver2'     -> 'ver2'     一致
丸数字      '①項目'       -> '1項目'    / '1項目'    -> '1項目'    一致
```

**ひらがなはカタカナへ畳む**（2026-09-07 決定）。NFKC は半角カナと濁点までしか畳まず、ひらがなとカタカナは別の符号位置で残る。索引の目的から見てこの2つを別の語として持つ理由が無く、書いた側の表記を覚えていないと同じ語を2回打ち直すことになる。

`ぁ`〜`ゖ`（U+3041〜U+3096）と繰り返し記号 `ゝゞゟ`（U+309D〜U+309F）に 0x60 を足す。`ゔ` は `ヴ` になる。`ヷヸヹヺ` にはひらがなが無いので対象外。畳む向きをカタカナにするのは、半角カナが NFKC でカタカナへ寄るため行き先が1つに揃うから。

意図してカナを書き分けている箇所も1つに潰れる。カタカナ語をひらがなで打って0件になる方が実害が大きいと判断した。

Joplin 本体の `normalizeText_()`（NFC + Latin diacritics マップ）では全角・半角が揃わないため、これを流用しない。

### FR-2 トークン化

**CJKAnalyzer 互換の1方式のみ。設定で切り替えるモードは持たない。** スクリプト境界で分割し、
CJK 連続部分は重なり 2-gram、ラテン語・数字は1トークンとして保つ。

正規化後の全文字を bigram にする方式は採らない。`PI` で `API` が引けてしまい精度が落ちる。
出典と実測比較は `docs/evernote-research.md`。

**このアナライザ内部にはスクリプト判定がある。これは許容する。**（2026-09-06 決定）

| | 可否 | 理由 |
|---|---|---|
| トークナイザ内部で文字種を見て切り方を変える | 許容 | 索引時にもクエリ時にも同一の関数が通る。索引は1つで、クエリの内容によって投げ先が変わらない |
| クエリの文字種で索引・検索経路を分ける | **不可** | Joplin 本体がこれをやって取りこぼしている。同じノート集合を別々の索引に別々の方法で問い合わせると結果が一貫しない |

この2つは「モード」という同じ言葉で呼ばれうるが、別物として扱う。

**索引は2列持つ。**

| 列 | 内容 | 用途 |
|---|---|---|
| `tok` | スクリプト境界で分割したトークン列（CJK は重なり bigram） | フレーズ検索 |
| `tail` | 各連続部分の末尾文字 | 1文字クエリの補完 |

末尾文字の unigram を `tok` に混ぜてはならない。**位置がずれてフレーズ検索が壊れる**（実測確認済み）。

**クエリ長による分岐**

- 2文字以上: `tok` のフレーズ検索。位置情報を使う。AND では `国産の日産車` が `国産車` で誤ヒットする
- 1文字: `tok` の前方一致 OR `tail` の完全一致

### FR-2b 打鍵中の語は前方一致（2026-09-07 決定）

**クエリの末尾の語だけを前方一致で引く。空白で区切られた語は完全一致で引く。**

```
mahaakassap    → 前方一致。mahaakassapa に当たる
mahaakassap␣   → 完全一致。当たらない
test␣api       → test は完全一致、api だけ前方一致
```

ラテン語・数字は1トークンで索引するため、完全一致だけだと語の途中まで打った状態で0件になる。CJK は bigram なので部分が当たり、latin だけ当たらないという非対称があった。

**打っている途中の語だけを伸ばす。** 空白を打った時点でその語は確定したものとして扱う。全ての語を前方一致にすると `api` が `apiece` に当たるのを止める手段が無くなるが、この規則なら空白を1つ足せば絞れる。

判定は正規化前の生のクエリで行う。`normalize()` が末尾の空白を落とすため、正規化後では区別が付かない。

CJK 側は影響を受けない。bigram は全て2文字なので、末尾トークンを前方一致にしても一致する集合が変わらない（実測確認済み）。索引の内容は変わらないので、この変更で作り直しは発生しない。

### FR-3 markdown 記号をまたぐ一致。改行は語の区切り

索引対象テキストは markdown 記号を除去したうえで生成する。`屋根の**防水**工事` に対して `防水工事` が一致すること。**記号を落とした位置には何も入れない。**

**改行は語の区切りとして扱い、行を連結するときは常に空白を入れる。** 日本語でも同じ。`屋根の防水\n工事を実施した` は `防水工事` で引けない。

保留にしていた「除去して連結するか、空白に畳むか」の結論（2026-09-06）。連結を採らない理由は3つ。

- **markdown の仕様が改行を空白として描画する。** 段落内の単独改行は HTML 上で空白になり、Joplin のプレビューでも `雨\n傘` は間が空いて見える。索引が表示と違う解釈をすると、見えているものと引けるものがずれる
- **連結すると存在しない複合語ができる。** `昨日は雨\n傘を買った` が `雨傘` で引ける。誤ヒットは利用者の側から取り除けない。空白を入れて起きるのは取りこぼしだが、より短い語で引き直せば届く
- **語の途中で改行される経路がほとんど無い。** Joplin のエディタは折り返しを表示上で行い、改行文字を入れない。本文の改行は利用者が Enter を押した箇所か外部から貼った本文で、前者は文や節の切れ目にある

### FR-4 上限とランキング

- 検索結果に固定の 20 件上限を設けない。上限を設ける場合は関連度順で切る
- 順序は「タイトル一致 > 一致数 > 更新日時」を基本とする。具体的なスコア式は実測して決める
- **表示上限で切ったときは、切ったことを状態行に出す**（`55 件中 50 件を表示`）。並び順がタイトル一致を最優先にするため、タイトル一致が上限を超えると本文一致が1件も画面に出ない。件数だけを出すと「無い」と区別が付かない

### FR-5 索引の維持

- 初回構築はバックグラウンドで進め、UI をブロックしない
- Joplin 本体の DB を読むだけで、書き込まない

**変更のあったノートだけを入れ直す。** `joplin.workspace.onNoteChange()` が渡す id を1件ずつ取得して索引する。変更1件のたびに全件を取り直さない。処理中に来た id は捨てずに積み、同じ id は1回に畳む。

**イベントに頼り切らない。** `onNoteChange` は選択中のノートしか通さない（本体 `JoplinWorkspace.ts` が `selectedNoteIds` で絞っている）。同期で降ってきたノート・別ウィンドウでの編集・一括操作はイベントが来ない。既定60秒ごとに `id` と `updated_time` だけを全件取得して索引と突き合わせ、食い違った分の本文だけを取りに行く。

**全件取得は `id` の昇順で行う。** 既定の `updated_time` 順は一意でも不変でもないため、offset を進めるページングの途中でノートが保存されると、以降のページ境界でノートが1件ずつ静かに落ちる。落ちたノートは索引から削除される。

**索引更新の失敗を画面から見えるようにする。** 直近の更新結果（入れ替えた件数・直近のエラー）を保持し、ダイアログの状態行に出す。検索自体は既存の索引で動き続けるため、無音だと更新が止まっていることに気づけない。

### FR-6 UI

- 独自ダイアログでインクリメンタル検索・キーボード選択・ノートへのジャンプ
- IME 変換中は検索を走らせない（`compositionstart` / `compositionend` を見る）。本体の GotoAnything にはこのガードが無く、確定前の中間状態ごとに検索が走る
- Ctrl+P への割り当ては、本体の `gotoAnything` を手動で外す必要がある（`KeymapService.registerCommandAccelerator()` は既存バインドを上書きしない）。手順を README に記載する

### FR-7 索引のバージョン管理と再構築

索引スキーマやトークン化アルゴリズムを変更すると既存索引は無効になる。

- 索引 DB に `meta` テーブルを持ち、`analyzer_version` / `schema_version` を記録する
- 起動時に実装側の値と `meta` を突き合わせ、不一致なら再構築が必要である旨を確認ダイアログで提示する
- 承諾されたらバックグラウンドで全再構築する。拒否されたら既存索引のまま動作を続ける
- 先例: Jarvis プラグインが同方式（埋め込みモデル変更を検知して rebuild を促す）を採っている


## 5. アーキテクチャ方針

検索コアとプラグイン外殻を分離する。

- **検索コア** — 正規化・n-gram 生成・索引構築・クエリ実行。Joplin API に依存しない純粋な Node + SQLite モジュール。ヘッドレスで単体テスト可能
- **プラグイン外殻** — `joplin.data` からのノート取得、`joplin.require('sqlite3')`、UI、コマンド登録。Joplin デスクトップ上でのみ動作確認できる

この分離により、上記の検証のほとんどを Joplin デスクトップ無しで回せる。

`joplin.require('sqlite3')` と `joplin.require('fs-extra')` はプラグイン API として公式に提供されており、Jarvis プラグインが同じ方式で独自 SQLite を運用している先例がある。
